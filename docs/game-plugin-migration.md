# Playnite 资料与识别迁移：开发检查点 04

> 本文保留架构开发阶段的设计与验证范围。文中的 `checkpoint/...` 中间标签与 `outputs/...` 证据为本地开发记录，不随公开 Git 历史上传；公开版本的复现与恢复以 [验证记录](verification.md) 和 [回退说明](plugin-rollback.md) 为准。

[运行管理](plugin-runtime.md) · [模块边界](plugin-boundaries.md) · [回退](plugin-rollback.md)

2026-10-15 在 `feat/core-plugins` 完成第一批真实功能接管。Playnite 导出解析、进程匹配和游戏分类现在由
`leisurelog_plugins.playnite` 提供，核心处理服务不再构造 GameClassifier，也不再查询游戏目录。
活动仍由 ActivityWatch 提供；目录里的累计游戏时长只留在原始资料快照，不生成活动或增加 Session 时间。

## 职责与数据路径

| 位置 | 负责什么 |
|---|---|
| domain/game_catalog.py | 不可变文件文本、目录导入提案、目录快照与游戏 ID 匹配协议 |
| adapters/catalog_files.py | 读取宿主配置的两个文件；导出最多 10 MB、绑定最多 1 MB，无路径参数 |
| leisurelog_plugins/playnite.py | 解析 Playnite 格式与 YAML 绑定、排除共用启动器、匹配已安装游戏 |
| services/plugin_access.py | 读取前后检查授权，验证提案及匹配结果，由宿主生成分类字段 |
| services/plugin_runtime.py | 受控读取、调用预算、激活代数、撤销、批次分类与提交前检查 |
| services/games.py | 经验证的目录导入用例，通过目录与处理接口完成变更 |
| repositories/games.py | 保留原始快照、替换当前目录、提供事务内不可变快照 |
| game_integration.py | 唯一游戏资料组装点；绑定固定官方包、管理 SQLite 事务和旧封面兼容入口 |
| api/games.py | 保留现有 URL，通过宿主接入；不直接读取 Playnite 或组装目录仓库 |

手动导入与自动同步共用 GameCatalogHost.refresh：先通过运行管理器在有预算的工作线程读资料，
再取得 SQLite 写锁，保存来源快照与处理资料，并在同一事务重新分类。
分类读取本次事务里的新目录，不依赖另一个连接尚未看到的提交。
最终提交与停用/撤权在宿主中明确排序：旧代数、已经停用或发生故障的读取不能提交，整次导入回滚。
目录与封面读取共用独立资料通道，分类仍在原调用通道内串行；两者同属宿主管理和全局工作槽上限。
资料读取不会仅因占用同插件的调用位置把健康匹配挤成 unknown；有目录与分类贡献时为两类调用保留容量。
官方资料源、封面索引与匹配对象分别持有状态，不能把这个并行行为理解为任意插件对象自动具备线程安全。

自动同步只接受一个可选的“同步前增强”调用，不导入 Playnite 或游戏目录仓库。
增强缺失、损坏、抛错、超时、停用或返回错误结构时，本轮仍继续保存 ActivityWatch 数据并推进成功窗口。
活动来源自身失败仍保持原来的错误与进度语义，不伪造采集成功。

## 匹配身份与优先级

顺序保持为：人工覆盖 → 记住的规则 → YAML → 普通插件建议 → 目录匹配 → unknown。
普通插件建议继续使用 `plugin:<ID>@<版本>`。目录匹配只允许提出 GameMatch(game_id)，
宿主验证该 ID 属于本批目录且已安装，再从保存资料生成名称、标签与 `playnite:<UUID>` 来源。
插件不能自行提交 manual 来源或用另一套名称/标签覆盖资料；原来的 SDK ID 仍供游戏改名、类型选择和历史统计使用。

每次重建只读一次保存目录，窗口与网页解析使用同一不可变批次视图。无对应进程的活动跳过游戏插件调用，
不为全部电脑活动创建无效工作项。整条插件分类链仍共享 0.25 秒预算。
匹配逻辑保持原有保守规则：未安装不匹配，共用进程需要标题条件，同一进程有多个匹配候选时不猜测。

## 默认选择、权限与恢复

源码默认组装一个官方模块 `leisurelog.playnite`，版本 0.1.0；描述与模块绑定由宿主固定，配置/HTTP 不能选择代码路径。
未出现过插件选择文件时，为兼容原内置功能使用固定的首次默认授权；它不是给后续插件自动授予权限。
已经保存的选择，包括空集合、停用或撤权，一律优先；损坏配置继续保留并阻止管理写入。
显式 `create_app(..., plugins=())` 提供无功能插件的核心实例，非空显式集合只登记调用者提供的定义。

当前模块声明 `game-catalog` 与 `classifier`，需要：

- `files.import`：读取固定的游戏导出及进程绑定。
- `games.catalog.propose`：提交有大小与格式限制的目录提案，由核心事务存储。
- `games.catalog.read`：分类时读取保存的不可变目录。
- `activity.details.read` 与 `classification.propose`：对统一活动提出匹配。

公共 SDK 没有数据库连接、完整 Repository、事务函数、导入票据或全局 app。
GameCatalogImport 验证统一 UUID、唯一性、大小、不可变集合和字段类型，拒绝重复 JSON 键及非 JSON 数值。
它不解释具体导出格式；Playnite 格式由插件解析，固定资料槽在提交前核对源 ID 对应。
身份命名空间由宿主的保存目录快照提供，通用分类封装不写死具体来源。
当前资料槽只有 Playnite；其他游戏库需要另行设计来源身份与路由，不能并行覆盖这张目录。

缺失/损坏导出属于可恢复读取问题：保留旧目录，插件仍可用，状态增加 `catalog_error`，文件恢复后再次读取即可清除。
意外异常、无效贡献/匹配或调用超时属于运行故障：撤销访问、撤下匹配、显示 failed。
手动明确启用或下一次程序启动才重新尝试，不能在每个活动片段中无限重试。
目录读取默认最多 2 秒；未真正返回的工作继续占槽，停止超时期间不能启动同一插件的第二份实例。

旧封面页面尚未成为页面贡献，但兼容读取已经通过运行管理器和同一文件权限。
停用/撤权、包缺失或调用失败时返回空封面，不绕过授权直接读导出；已交付给浏览器的数据不能追溯收回。
停用本身不重写历史、删除目录或清除人工选择。显式完整重处理继续按当前启用集合生成派生分类，原始版本与人工覆盖保留。

## 接口与使用

原有 `GET /api/games/playnite`、`POST /api/games/playnite/import` 和统计/偏好 URL 保持。
无效导出返回 422；停用、失效、撤权中或繁忙的导入返回 409。管理状态仍使用 `/api/plugins`。
重新启用请求示例：

```json
{
  "grants": {
    "leisurelog.playnite": [
      "files.import", "games.catalog.propose", "games.catalog.read",
      "activity.details.read", "classification.propose"
    ]
  }
}
```

首次默认配置代数为 0，没有选择变更时不创建文件。第一次选择变更原子写入 `plugin-state.json`；重启遵从保存选择。
数据库、规则、导出与插件选择应位于独立开发数据目录。稳定目录、日常服务和现有安装包没有自动切换。

## 检查、对照与回退

本轮移除 7 处已登记的旧依赖，只剩 main 对游戏统计与偏好路由的 2 处历史耦合。
新增明确的组装许可仅允许 game_integration 访问目录仓库；业务、普通 API 和活动仓库不能借此导入游戏实现。
页面/偏好/分析仍在核心原位置，不将这次接入迁移称为整套游戏功能拆分完成。

测试覆盖大小、来源一致性、授权、在途撤销、过期票据、超时、无效 ID、未安装 ID、批次读取、损坏/恢复、
原子回滚、停用后重启、包缺失，以及实际源工作抛错/超时/无效匹配后，SQLite 仍保存核心活动并再次成功同步。

`scripts/verify_game_migration.py` 从 runtime-03 提取实际代码，在新建的合成数据库与当前代码对照 9 个阶段；
比较活动、Session、分类来源、全部时长汇总、游戏统计、原始活动和资料快照。
还把新版合成库通过 SQLite backup 复制，交给旧代码读入及重处理，验证兼容 0013。

```powershell
python scripts/verify_game_migration.py --output outputs/game-catalog-parity-fresh
```

输出必须是本工作树 outputs 下尚不存在的目录，脚本不删除旧证据。报告及对照资料含合成输入，继续被 Git 忽略。
旧 SDK 不认识新增的目录权限，会保留配置、报告 configuration_invalid，并继续旧核心采集；
正式回退应保存当前配置后恢复目标检查点配套选择文件，不能把新增权限文件当作旧代码兼容配置。

本轮不增加 Alembic 迁移或依赖。PyInstaller 配置补充固定官方模块的隐式导入，但没有重新生成安装包、
执行干净 Windows 安装验证、发布独立插件包、安装中心或 GitHub CI。
线程预算和权限封装仍仅用于受审查官方代码，不具备恶意第三方代码的进程隔离、CPU/内存强限制。
