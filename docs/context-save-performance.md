# 人工用途确认的保存性能

“待确认 → 确认用途”的一组可以包含当前日期范围内最多 1000 条来源记录。
选择“仅修改这次记录”不应重新识别整段历史的应用、网页或游戏。

## 原因与改动

此前保存人工用途后复用来源更新的范围规划：沿同来源、设备、窗口流的连续活动和旧 Session 扩张，再重新分类、解析网页、计算计时、生成 Session 和每日汇总。多个离散选中范围可能反复扩张到同一连续区间，因此一次局部确认也可能发生大量数据库往返。

现在单次用途/项目修改和“恢复自动归属”使用独立的归属更新流程：

1. 保存所选记录的人工选择，按来源窗口读取已有解析结果，保留窗口与网页事实、分类、计时和原始数据。
2. 重新求解这些窗口的用途/项目，批量更新真正改变的归属；保留父窗口人工选择与网页片段的继承语义。
3. 根据已有 Session 的事件顺序，仅更新受影响的完整 Session 及相邻 Session。互不相连的处理片段分别合并，不能越过未参与的活动。
4. 对存在重叠事件的窗口流，保守地从该流已有解析结果重建 Session，避免跨边界合并改变时长；仍不重跑来源读取或内容分类。
5. 批量替换相关 Session、关联和每日汇总，与人工选择在同一事务提交。失败一起回滚；提交完成后才返回成功。

服务负责归属与 Session 规则；数据库查询、分批参数和批量持久化保留在 repositories。
插件继续通过原公共接口运行，没有把数据库连接或 Repository 暴露给插件。
数据库结构继续使用 0013，无迁移或历史数据清理。

## 验证方式与边界

用独立合成数据库对比旧流程与新流程，同时把新结果与完整重算结果逐表比较。
检查单条与 1000 条批量修改、重复保存、恢复、Session 拆分与双侧合并、重叠与相同起点、多设备/多流、跨午夜、AFK、人工计时和失败回滚。

最终固定输入对照如下（Windows，同一 Python 3.11 环境）：

| 合成样本 | 原流程 | 新流程 | SQL 语句数（原 → 新） |
| --- | --- | --- | --- |
| 800 条连续活动，修改 1 条 | 1.3943 秒 | 0.0177 秒 | 5360 → 22 |
| 800 条连续活动，修改 25 条 | 5.3350 秒 | 0.0427 秒 | 14960 → 70 |
| 30000 条活动，修改 1000 条 | 未运行 | 1.7982 秒 | 新流程 2042 |

Python 3.11.9 与 3.13.9 完整回归分别通过 529 项；前端 51 项通过，Ruff、架构与空白检查通过。
新增 11 项测试涵盖上述边界，并将每次局部更新及恢复与完整重算逐表对照。
这些是特定环境的合成基准，不是用户真实数据或所有电脑的时延承诺。

保存“以后同一应用/网站”等规则仍需要全历史影响预览和完整重建；删除规则、撤销历史修改也继续使用原有完整重建流程。
本次重点是无规则的人工用途/项目确认与恢复；多个写操作仍在 SQLite 中串行。
上下文更新会读取相关窗口流的 Session 排序元数据，历史极大或大量重叠时仍有进一步优化空间。
